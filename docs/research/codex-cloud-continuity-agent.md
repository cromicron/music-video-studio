# Codex Cloud continuity: independent research as of 7 November 2026

**Recommendation:** use the current published Cloud environment for reproducible tools, keep one ongoing task for the live work, and keep authoritative project state in versioned repository files that new tasks explicitly read through concise `AGENTS.md` guidance. Use ChatGPT project context/memory as supplementary recall where the actual surface supports it. Do not implement local CLI memory flags or shell lifecycle hooks and describe them as Cloud persistence.

This is research, not an implementation or a successful fresh-task recall test. Root owns the consolidated project record and startup changes. Only this research file was created for this assignment. The prior media-transfer investigation was separately saved in `productions/join-me-in-life/full-film/tools/FLOW_KEYFRAME_TRANSFER.md`; no browser run or new production was started.

## Current official support and its limits

Sources below were read directly on **7 November 2026**, including their Markdown bodies and surface-specific sections. Most are living pages without a publication date; retrieval date is not a claim about release date. The old developer URL redirects to a different, explicitly legacy page.

| Capability | What the current primary source establishes | What it does not establish |
| --- | --- | --- |
| New Cloud task | “Each new task gets its own isolated workspace from the published environment.” [Current environments](https://learn.chatgpt.com/docs/environments/cloud-environments) | New chats do not share one live writable checkout or automatically inherit another task's uncommitted memory. |
| Resume an existing Cloud task | “Existing task: continues with its own saved files, including uncommitted changes and installed tools.” The same task can be reopened across devices. [Current environments](https://learn.chatgpt.com/docs/environments/cloud-environments#reuse-and-update-saved-state) | Saved files are not proof every fact from the transcript is presently in model context. |
| Saved VM retention | “By default, a task's saved VM state is recoverable for up to seven days after you last start a turn or resume the task.” [Current environments, VM specifications](https://learn.chatgpt.com/docs/environments/cloud-environments#vm-specifications) | Not permanent archival storage, an indefinite-running process guarantee, or a seven-day memory database. |
| Publish/republish | Publishing captures a prepared filesystem. Republish affects new tasks; existing tasks retain their own state. Repository refresh happens in the background while preserving dependency caches. [Current environments](https://learn.chatgpt.com/docs/environments/cloud-environments) | No documented automatic merging of task branches, unpublished files, or task-specific decisions into a shared memory record. Check actual branch, SHA and dirty state. |
| Current setup fields | **Install script** installs dependencies/prepares assets; **Start skill** starts services and checks readiness. [Current environments, installation/startup](https://learn.chatgpt.com/docs/environments/cloud-environments#customize-installation-and-startup) | Running a setup script does not itself prove the model read or adopted memory before its first substantive answer. The page does not promise per-turn execution of a memory loader. |
| Repository instructions | “Codex reads `AGENTS.md` files before doing any work.” The documented chain is global guidance, then project-root-to-current-directory guidance, one applicable file per directory; overrides take precedence; default combined limit is 32 KiB. [AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md) | A large index or every linked file is not automatically loaded merely because it exists. The guide's diagnostic CLI commands are local-client examples, not commands that remotely configure Cloud orchestration. |
| Web project context | Project chats share uploaded files, project instructions and connected sources. Each chat keeps its own messages/results; pinning adds no access/context. [Projects and chats](https://learn.chatgpt.com/docs/projects) | A ChatGPT project is not automatic synchronization of a repository folder, task filesystem or every past chat transcript. The documented web Projects surface must be distinguished from a Cloud environment. |
| Native memories | “ChatGPT web uses ChatGPT memory, while local Codex clients use a separate local memory store and controls.” Web/Work settings live under Personalization; Work does not use local Codex memory controls. [Memories](https://learn.chatgpt.com/docs/customization/memories) | Adding `[features] memories = true` to a VM does not establish that the personal cloud-orchestrated task will use that local store. |
| Local Codex memories | Off by default, under the connected host's Codex home. Eligible idle chats are summarized in the background; short/active sessions, low quota and external-context settings can affect generation. [Memories](https://learn.chatgpt.com/docs/customization/memories) | Not immediate end-of-chat persistence, complete history ingestion, or a substitute for required repository rules. The source explicitly calls memories a helpful recall layer. |
| Cloud hooks | “Cloud orchestration supports only Global MCP hooks” in supported managed Enterprise configurations. Personal accounts and Work Cloud without local-computer access do not use those enterprise hooks. Local command/prompt/agent handlers, local/plugin/environment hooks and `SessionEnd` MCP hooks are unsupported there. [Hooks](https://learn.chatgpt.com/docs/hooks#hooks-with-cloud-orchestration) | A checked-in `SessionStart`/`SessionEnd` shell hook is not a dependable personal Cloud startup/save mechanism, even if tool execution happens on a local machine. |
| Computer History | macOS desktop feature, off by default, collecting allowed app interaction context into local summaries/memories. [Computer History](https://learn.chatgpt.com/docs/customization/computer-history) | Not a Linux Cloud VM history collector or automatic import of all project/chat history. |

The current environment guide also says repository skills are available to Cloud tasks, but personal skills on a local computer are not synchronized automatically. Preserve reusable project skills in the repository or another explicitly accessible source; an installation on one transient task is not a universal skill deployment.

## Legacy behavior must stay labelled legacy

The old URL `https://developers.openai.com/codex/cloud/environments` was fetched and redirected to [Codex Cloud (Legacy)](https://learn.chatgpt.com/docs/environments/cloud-environment). That page applies to remaining Code Review, Linear and GitHub integration workflows. It describes setup and maintenance scripts, checkout at selected branch/SHA, a **12-hour container cache**, and setup-only secrets.

Those statements must not be used to explain the newer published-environment / Install script / Start skill experience. The current page has different saved-state and secret-delivery semantics. Likewise, the [2–6 November release page](https://learn.chatgpt.com/docs/whats-new/november-2-6-2026), dated **4 November 2026**, discusses dots/iOS/desktop improvements; it does not establish a new universal Cloud project-memory service. “Newest release notes” alone do not answer the continuity question.

## Community implementations and observed failures

These are concrete inspected artifacts, not vendor marketing. None was installed or run here, and source inspection is not proof of end-to-end recall quality.

### 1. Langfuse JS: concise project guide and reproducible environment scripts

Inspected `langfuse/langfuse-js` at commit **`ee0d271a28eb442521a2cef6e53fa85199c54c02`**, whose commit timestamp is **6 November 2026, 15:19:48 UTC**. The repository has a practical [AGENTS.md](https://github.com/langfuse/langfuse-js/blob/ee0d271a28eb442521a2cef6e53fa85199c54c02/AGENTS.md) with task routing, commands, verification, source ownership and protection of existing edits. Its [setup script](https://github.com/langfuse/langfuse-js/blob/ee0d271a28eb442521a2cef6e53fa85199c54c02/scripts/codex/setup.sh) pins pnpm and installs from the lockfile, preserves an existing `.env`, and builds once. Its [maintenance script](https://github.com/langfuse/langfuse-js/blob/ee0d271a28eb442521a2cef6e53fa85199c54c02/scripts/codex/maintenance.sh) refreshes dependencies.

**Useful method:** short authoritative instructions, exact verification commands, deterministic setup, no destructive reset of existing work. **Boundary:** its current contributing guide still uses the legacy setup/maintenance terminology. A recent commit date does not make that interface the new Cloud interface or demonstrate memory recall.

### 2. A portable Cloud baseline: dependency fingerprints, not “memory”

Inspected `yanniedog/cursor-global-workflow` at **`d4e80ebfb2cbe0e7b0842a5ee6de87abf687370a`**, timestamp **12 October 2026, 10:53:41 UTC**. ### 3. A real continuity implementation whose hook wiring is local-only

Inspected `jugol/codex-agent` at **`679a2b374968a27241c658517d09c246adb10e3d`**, timestamp **20 August 2026, 05:40:32 UTC**. Its [README](https://github.com/jugol/codex-agent/blob/679a2b374968a27241c658517d09c246adb10e3d/README.md) and [AGENTS.md](https://github.com/jugol/codex-agent/blob/679a2b374968a27241c658517d09c246adb10e3d/AGENTS.md) specify a compact startup brief, task-directed retrieval of a few whole notes, approved-versus-candidate knowledge, source provenance, bounded memory budgets and one writing task at a time. Real scripts and hook configuration implement that protocol.

**Useful method:** keep the current brief compact; retrieve detailed evidence when relevant; separate decisions from proposals; reconstruct context from inspectable files rather than replaying a giant transcript. **Boundary:** it requires a local synchronized vault and trusted local hooks. Its own requirements exclude a generic cloud-only chat without folder access. Do not copy its local `SessionStart` implementation into this Cloud task and claim automatic injection. Its optional external vault is not necessary for this repository's minimum solution.

### 4. A fresh-task failure despite passing setup tests

[OpenAI Codex issue #56920](https://github.com/openai/codex/issues/56920), opened **25 October 2026**, reports a published Cloud environment with Install script, Start skill, workspace/repository instructions and indexed context. Setup checks and seven bootstrap tests passed. A fresh ordinary prompt still received an answer that had not inspected the files; an explicitly requested diagnostic then read them successfully. The issue remained open when checked, with only an automated duplicate-suggestion comment.

The author carefully states that the model's claimed delayed instruction arrival was **not independently verified against a server prompt trace**. This is one user report, not a confirmed universal product defect. Its direct lesson is still sound: file existence, a passing loader and an explicitly seeded diagnostic do not measure automatic first-answer recall. Keep these acceptance tests distinct.

## Minimum reliable architecture for this studio

1. **One authoritative repository record.** Extend the existing studio structure rather than add a parallel memory product. A short current-state entry should identify the goal, approved direction, rejected approaches, current deliverable/hash, next action, unresolved access and spending scope. Decisions and dated evidence stay in their existing records; an index points to them. Distinguish proposed, tested, accepted and superseded claims. Raw histories belong behind source references, not inside every startup prompt.
2. **A compact entrypoint that actually reaches the task.** Keep `AGENTS.md` concise and make it tell a new task to read the current project index/state before substantive work. Verify the actual working directory and instruction chain. If tasks start at `/workspace` outside a Git root, a workspace entrypoint must point to the repository; do not assume a nested repository guide was automatically discovered. Preserve standing instructions when constructing that entrypoint.
3. **Current Cloud installation/startup.** Store reproducible runtime/readiness commands and the context-reading procedure in repository-owned code/docs. The Install script prepares files/tools; the Start skill provides the documented service/readiness instructions. Publish and test the environment. Do not describe any script output as model-context injection unless a fresh-task test proves the actual behavior. Do not depend on an unsupported personal Cloud shell hook.
4. **Checkpoint substantive changes during work.** Save state when an important decision, accepted artifact, rejection, permission or blocker changes, and before a planned handoff. Do not wait for `SessionEnd`, which is not a supported personal Cloud save mechanism. Use the same task for ongoing work; source-control checkpoints and durable artifact storage carry completed state to future isolated tasks. Commit/push or external writes must stay within the user's existing authorization.
5. **Track branch and source freshness.** New-task bootstrap should inspect repository URL, branch/SHA, dirty state and the latest checkpoint. Preserve uncommitted work and divergent branches; do not reset blindly to a published snapshot. Treat background repository refresh as platform behavior, not proof that the newest unmerged task work is present.
6. **Use native recall as an addition.** Where available, shared ChatGPT project instructions/sources and account memory help connect chats. They should point to the canonical project record and reduce repeated explanation. They do not replace exact release hashes, rejection records, paid-credit authorization or current account access checks. Do not promise that inaccessible historical chats have been consolidated.

This architecture needs no new memory subscription, database, local-vault product or vector store. The current repository already supplies much of the structure. The main improvement is a tested retrieval-and-checkpoint discipline on the correct Cloud surface, with an explicit coverage record of which histories were actually accessible.

## Acceptance tests that would prove the relevant behaviors

These are proposed tests for root to run after implementation; they were not executed during this research.

- **Same-task resume:** create a harmless unique checkpoint file and uncommitted edit, allow the active turn to finish, reopen the same task, then verify exact content and branch state. This checks saved filesystem continuity, not cross-task recall.
- **New-task recovery:** start a genuinely fresh task in the published environment. Use a normal continuation request that does not name the memory file or seed expected facts. Before evaluating, wait for environment startup to finish. Score whether it independently retrieves the current goal, last accepted artifact, rejected approach and next action from the real source record, with the correct provenance and no fabricated access.
- **Change propagation:** change one harmless fact in the authorized canonical checkpoint, save it through the intended durable route, then start another fresh task. It must recover the revised value and treat the earlier value as superseded. Record environment publication version and repository SHA so a stale checkout can be distinguished from failed recall.
- **Unavailable source:** make a test source deliberately unavailable in an isolated test setup. The agent should identify the missing source and avoid claiming complete memory. It should still use independently available context.

A structural check can validate links, schemas and required fields. It cannot replace these behavioral probes. Do not seed the verifier with the expected answer, confuse a prompted “read this file” test with automatic retrieval, or declare memory reliable merely because a new configuration file exists.
